# Agent harness

The software factory is the workflow; this harness implements it for Claude
Code with commands, skills, fresh agents, and deterministic scripts. Read
[FACTORY.md](FACTORY.md) for tiers, artifacts, lifecycle and human gates.
Bootstrap instructions are in [setup](.harness/docs/setup.md).

## Pipeline

```text
explore → intent 🖐 → spec + tasks 🖐 → implement → verify → review 🖐 → ship 🖐 → archive 🖐
```

`🖐` = human gate. Agents carry out the work between gates. This is the STANDARD
path; DEEP adds architecture and program-design decisions, while FAST skips
OpenSpec planning and archive.

| Stage | Command | Output | Gate |
| --- | --- | --- | --- |
| Explore / intent | `/explore` | Workflow choice and `openspec/changes/<slug>/intent.md` for STANDARD/DEEP | 🖐 accept intent |
| Spec + tasks (STANDARD) | `/crystallize` | `proposal.md`, delta `specs/`, `design.md`, `tasks.md` | 🖐 accept specs/design/tasks |
| Architecture (DEEP) | `/crystallize` | `proposal.md`, delta `specs/`, architectural `design.md` | 🖐 accept architecture/specs |
| Tasks (DEEP) | `/shape-change <slug>` | `program-design.md`, `tasks.md` | 🖐 accept program design/tasks |
| Implement | `/dev-change <slug> <group>` | Code, tests and docs on one task-group branch; worktree optional | — |
| Verify | Fresh maintainability reviewer, then verifier | Code-shape review, scenario checks and full-gate evidence | — |
| Review | `/review` | Review findings against the diff and delta specs | 🖐 review results and authorize shipping |
| Ship | `/commit-push-pr` | Final gate, commit, push and PR | 🖐 merge the PR |
| Archive | `/archive-change <slug>` | Approved deltas merged into `openspec/specs/`; change archived | 🖐 approve the proposed spec diff before applying |

Repeat implement → verify → review → ship for each task group. Archive only after
all groups have merged. For DEEP uncertainties, an optional `/spike` follows
accepted intent; accept its findings before continuing to architecture.

`/opsx:*` and the `openspec-*` skills are OpenSpec's low-level tooling,
regenerated by `openspec update`. Enter new work through `/explore`; the factory
commands add the planning, verification and human gates around that tooling.
Resume accepted tasks directly with `/dev-change`.

## Start here: the development loop

Slash commands below are prompts to the agent; shell commands run in the
repository root. Replace `add-rate-limiting` and group `1` with your change and
task group. [FACTORY.md](FACTORY.md) defines the workflow rules; this guide shows
how to use them.

### 1. Prepare the checkout

For a new clone, follow [setup](.harness/docs/setup.md), including Python 3.12+,
uv and OpenSpec. Then prepare application navigation:

```bash
make graft-install
export PATH="$PWD/.harness/bin:$PATH"
```

Installation uses Node.js 22.12+ to install the pinned Graft CLI separately from
application dependencies. It previews and installs the upstream `/graft` skill.
The PATH setting makes `graft` select the factory launcher in this shell; repeat
it in new shells. See [navigation](#application-navigation-with-graft) for scope
configuration and the optional model-backed build.

On an existing checkout, inspect `git status` before switching branches. Once
local work is saved and the preceding task group has merged, switch to the
configured base and pull it (`git switch main`, then `git pull --ff-only` when
the base is main). Start each dependent group from that updated base.

### 2. Check installation health

```bash
uv run --no-project --isolated --python 3.12 python factory doctor
```

Doctor inspects the installed factory without running project commands, Graft,
model calls or network requests. It checks metadata/configuration, required
files, command and hook wiring, executable entry points, OpenSpec structure,
Git ignore protections, Graft dependencies/wiring and eval configuration.
It does not open environment-secret files. The `uv` launcher may provision
Python on first use; doctor itself is offline. With Python 3.12 already active,
`python factory doctor` runs without that provisioning step.

Each error includes a stable category, path and remediation. Exit 0 means no
installation errors; exit 1 means repairs are needed; invalid CLI arguments
exit 2. Doctor also prints **freshness not assessed**: use the separate graph
check in step 5. Custom file contents are not compared against distribution
hashes, and installation ownership baselines are not required yet. Doctor checks
OpenSpec's directory/schema wiring; use `openspec validate` to validate specs.
Its offline schema check supports exactly one top-level `schema:` with an inline
name starting with a letter or underscore, followed by letters, digits,
underscores, dots or hyphens. Plain, single-quoted and double-quoted names and
trailing comments are supported. Empty values, unquoted null/boolean values and
duplicate declarations fail. Other YAML representations (such as aliases or block
scalars) require rewriting to this supported form. This check does not validate
the complete YAML document or resolve whether a custom schema is installed.
To inspect another installation, put the root option before the subcommand:
`python factory --root /path/to/project doctor`.

Command wiring checks recognize a single `bash .harness/scripts/cmd_<name>.sh`
invocation in a `bash` or `sh` fenced block, or a standalone ``!`bash ...` ``
directive. The script path may be quoted; an optional `$ARGUMENTS` and trailing
shell comment are supported. HTML comments and prose references do not count.
Custom shell wrappers or multi-command blocks need the supported preamble form
to pass this structural check; doctor does not interpret arbitrary shell code.

### 3. Agree on the change

Start with `/explore` and describe the problem. The agent chooses the workflow
size and records the relevant artifacts. Review each proposed artifact before
moving to the next command:

| Workflow | Commands and decisions | What you get |
|---|---|---|
| FAST | Agree on a small maintenance fix, implement on a `fix/`, `chore/` or `docs/` branch | A focused diff without OpenSpec artifacts |
| STANDARD | `/explore` → accept intent → `/crystallize` → accept specs/design/tasks | An implementable plan split into shippable task groups |
| DEEP | `/explore` → accept intent → optional `/spike` and accepted findings → `/crystallize` → accept architecture/specs → `/shape-change` → accept program design/tasks | Architecture decisions and explicit implementation boundaries |

When an accepted change already has tasks, resume its next eligible group
without repeating planning. `openspec/changes/<slug>/tasks.md` is the completion
checklist; its Context links identify the specs and design sections to read.

### 4. Implement one task group

```text
/dev-change add-rate-limiting 1
```

This claims `feat/add-rate-limiting-g1`, loads the selected group and implements
its behavior, tests and documentation. Branch existence prevents two sessions
claiming the same group. Prerequisite groups must have merged. During coding,
run targeted tests; before verification, run `make fmt` and inspect its edits.
For factory Python changes, also format `.harness/factory` with Ruff because
`make fmt` covers application source and tests.

For starter tooling changes, refresh distribution metadata with `make manifest`
after editing template-owned files. This preserves project overrides and records
hash history; it does not install dependencies or build the graph.

### 5. Prepare navigation and verify

```bash
.harness/bin/graft build
.harness/bin/graft check
```

Build creates the ignored structural graph for the configured application roots.
Check tests structural freshness; it does not rebuild. Empty application scope
reports **not applicable: no application sources configured**. Always rebuild
after changing application roots because checks use the last-built scope.

The agent then requests fresh maintainability review, resolves any concerns,
and requests a fresh behavioral verifier. The reviewer examines code shape;
the verifier checks accepted scenarios and runs `make check`. For factory
configuration/tooling changes it also runs `make evals` and `make harness-test`
as applicable. Failures return to implementation and affected verification.
The implementer does not duplicate the verifier's full suite immediately before
handoff. Verification completes with an uncommitted diff for the human to review.

**Graft network behavior:** pinned Graft 0.18.0 can update a machine-level cache
and launch a background registry request during CLI checks/queries, even with
telemetry disabled. The launcher prevents dotenv loading and graph auto-refresh;
those controls do not disable upstream version upkeep. This is why doctor checks
installation wiring offline and leaves graph freshness to explicit `graft check`.
Doctor success alone does not establish that the graph is current.

### 6. Review, ship, then continue

```text
/review
/commit-push-pr
```

Run `/review` on the prepared diff. Resolve findings before authorizing
`/commit-push-pr`; that command repeats the full gate, commits, pushes and opens
the PR. The human merges it. Then return to step 1 for the next task group.
After every group has merged, `/archive-change` proposes the canonical spec diff
for human confirmation. Archiving is a separate operation, never an implicit
side effect of completing or merging a group.

## Runtime entry points

| Entry point | Implementation |
|---|---|
| `/explore`, `/crystallize`, `/shape-change` | `.claude/skills/<name>/SKILL.md` |
| `/dev-change`, `/review`, `/commit-push-pr`, `/archive-change`, `/spike` | `.claude/commands/<name>.md` and `.harness/scripts/cmd_<name>.sh` (hyphens become underscores) |
| `/graft` | Upstream generated skill; `.harness/bin/graft` selects the isolated pinned CLI |
| Independent maintainability review | `.claude/agents/maintainability-reviewer.md`; fresh context, read-only |
| Independent verifier | `.claude/agents/verifier.md`; fresh context, read-only |
| Conditional security review | `.claude/agents/security-reviewer.md` |
| Git/base/task helpers | `.harness/scripts/lib/change.sh` |

`/opsx:*` and `openspec-*` are vendor tooling generated by OpenSpec. The factory
skills provide the human gates around that tooling. FAST needs no OpenSpec
artifact; its implementation and verifier start from the branch and repository.

`cmd_dev_change.sh` claims a branch and prints the selected task group plus
artifact paths. It does not dump the proposal, all specs, or the entire design.
The implementer follows the group's Context references; older STANDARD groups
remain usable through targeted searches without requiring program design.

The verifier discovers its own context from slug + group, or branch name for
FAST. No implementation reasoning is passed. Use a fresh agent/session in the
same checkout or claimed worktree; artifacts remain sufficient on other runtimes.
The definitions pin no model and inherit the invoking session's selection.

## Application navigation with `/graft`

Install Node.js 22.12+ and run `make graft-install`. This installs a locked CLI in
`.harness/graft`, previews the unchanged upstream skill, then installs that skill
and appends missing cache ignore rules without hooks, MCP, statusline changes or global agent configuration. Restart the
agent session if needed to discover `/graft`. Add the local launcher to the agent
shell before invoking the skill:

```bash
export PATH="$PWD/.harness/bin:$PATH"
```

Use `/graft` for the main application
implementation, excluding factory and harness tooling. For example, invoke:

```text
/graft Find where the application validates incoming requests.
/graft Show callers of validate_request without refreshing the graph.
```

Set `project.navigation.application_roots` in `.harness/template-manifest.json`
to the actual application directories, for example `["src"]` or `["app", "lib"]`.
The starter ships an empty list. Roots must exclude factory/harness tooling,
including tooling nested inside an otherwise selected directory. Roots containing
visible `factory/` or `harness/` subdirectories are rejected; select narrower
application roots instead. The launcher
passes these roots as upstream `--only-dir` options on every build. After changing
application roots, the implementer must run `graft build` before review. Upstream
owns fingerprint selection and validation; the wrapper does not inspect those
files. A check uses the last-built scope and does not detect manifest scope changes:

```bash
graft build
```

Its ignored `graft/` directory is a local, regenerable cache. Structural builds
need no model credentials; `--deep` enrichment is optional and outside required
checks. The launcher disables `.env` loading and query auto-refresh. Use `graft build
--deep` only when explicitly choosing model-backed enrichment.

Run targeted tests, then prepare the graph before independent review. Reviewers
check freshness and disable automatic refresh on every query:

```bash
graft check
graft ask "Where are requests validated?" --source
graft callers validate_request
```

For an on-demand review report, use `graft blast --base origin/main --format
markdown` (substitute the configured review base). Optional visual exports use
the upstream visualization CLI outside the required read-only review commands.
No committed graph or export is required.

A missing or stale application graph returns to the implementer for preparation;
reviewers never install, build or refresh it. Use targeted retrieval and relevant
impact evidence for review. Graph output supports navigation; source, accepted
design and behavioral checks remain necessary. Factory workflow boundaries apply
when using the upstream skill, including its examples that normally auto-refresh.

The local `graft check` gates structural freshness using the pinned CLI's JSON
report. Stale optional summaries or deep content are reported without blocking;
use source for current behavior. Enrichment is preserved, and refreshing it with
`graft build --deep` remains optional. Missing graphs, structural drift and
invalid upstream check results still fail.

When no application sources are configured, report **not applicable: no application
sources configured**. This starter currently has no application implementation;
validate navigation with an application fixture, and review factory/harness code
directly. This disposition does not skip growth checks or behavioral verification.

## Git mechanics

### Where the PR goes

`/commit-push-pr` does not assume `main`. It resolves the PR target in order —
first hit wins — and prints which one it picked before doing anything:

| # | Source | Set it with |
|---|---|---|
| 1 | The `--base` flag | `/commit-push-pr --base develop "fix(x): …"` |
| 2 | This project's configured default | `git config harness.baseBranch develop` |
| 3 | The remote's default branch (`origin/HEAD`) | whatever GitHub calls the default |
| 4 | `main` | last resort |

Set (2) once if your team merges to anything but its remote default — a release
train, a long-lived `develop`, a stacked feature branch. Use (1) for the
one-off. `gh pr create --base` is always passed explicitly, so the target is
visible in the command rather than inherited from `gh`'s own default.

The same resolved branch is what everything **diffs** against, so `/review` and
`/spike` show a branch relative to the trunk it will actually merge into. The
diff uses `origin/<branch>` in preference to your local copy — a trunk you never
check out goes stale, and a stale base makes already-merged work reappear in the
diff. So `/review` shows what the forge will show.

### Worktrees (opt-in)

The default claim is `git switch -c` in this checkout. Add `--worktree` only
when you are running **several sessions at once** and they would otherwise fight
over one working tree. One session at a time gains nothing and loses editor
visibility and a warm prompt cache.

```bash
/dev-change add-rate-limiting 1 --worktree   # session A → .worktrees/add-rate-limiting-g1
/dev-change add-rate-limiting 2 --worktree   # session B → .worktrees/add-rate-limiting-g2
```

- Each lands in `.worktrees/<slug>-g<N>` — inside the repo, so your editor sees
  it, and gitignored so `git status` and `make check` do not.
- The session calls `EnterWorktree` itself; open the path directly if you want a
  second editor window on it.
- **Cleanup is automatic.** A later `/dev-change` removes any worktree whose PR
  has merged, and deletes its branch. Nothing to remember.
- Removing one by hand, if you abandon the work:

  ```bash
  git worktree remove .worktrees/<slug>-g<N> && git branch -D feat/<slug>-g<N>
  ```

The branch is the mutex in both modes, so mixing them across sessions is safe:
whichever session creates `feat/<slug>-g<N>` first owns the group.

## Developer commands

```bash
make fmt          # edits source: formatting and safe lint/import fixes
make lint         # checks formatting, lint and types without fixing source
make test         # product tests
make check        # full non-mutating source gate
make check VERBOSE=1  # also show successful command output
make evals        # static factory invariants; no credentials
make evals-full   # static + behavioral prompt evals; needs Claude authentication
make harness-test # starter maintainer script tests
make manifest     # regenerate after template-owned changes
python factory doctor  # offline installation diagnosis; Python 3.12+
```

Run targeted tests during implementation. Run `make fmt` before handing work to
the verifier and inspect its changes. It can usually run once before verification,
but later edits may need another run. Formatting errors fail `make check`; the
verifier never fixes them. Return failures to implementation, then repeat affected
verification and human review.

The fresh verifier runs the full `make check`; after human review,
`/commit-push-pr` runs it again immediately before committing to catch later
edits. The implementer does not run a redundant full suite just before dispatch.
Removing that duplicate run is the main cost saving. Making checks non-mutating
keeps verification independent. Checks may write tool caches/test reports but
never auto-format or fix source files.

The reusable `run_quiet "label" command ...` helper in
`.harness/scripts/lib/run_quiet.sh` captures each command in a private temporary
log. Success emits one line (`✓ format`, `✓ lint`, `✓ types`, `✓ tests`,
`✓ doctor`, `✓ maintainability`, `✓ feature-docs`). Failure emits `✗ <label>` and the complete captured output,
preserving the exit status. Logs are removed after reporting; `VERBOSE=1`
includes successful output. Empty template source skips mypy and pytest's
no-tests-collected exit remains acceptable, as before; verbose output explains
these cases.

`make check` runs formatting, lint, types, product tests, offline doctor,
maintainability and feature-documentation checks in that order. It does not run
Graft or the eval suite recursively. `make check` gates the downstream product. For starter configuration changes,
also run `make evals`; for harness tooling run `make harness-test`. Behavioral
prompt evals are a separate authenticated check, not an expense imposed on every
product commit. Measurement format and representative scenarios:
[workflow runs](.harness/evals/workflow-runs.md).

## Hooks and final documentation check

| Mechanism | Responsibility |
|---|---|
| `pre_tool_dangerous.py` | Deterministic dangerous-command protection |
| `pre_tool_env_guard.py` | Protect `.env` across read/search/shell tools |
| `post_tool_secrets.py` | Detect secrets in edited content |
| `post_tool_lint.py` | Non-mutating checks on the edited Python file; silent success, useful failures |
| `check_feature_docs.py` via `make check` | Fail for missing `src/<feature>/CLAUDE.md` before shipping |

The former per-edit feature reminder is replaced by the final documentation
check. It needs no per-session state and sends no repeated reminders. Empty
package scaffolds, hidden/cache directories, and bare source-root files do not
require feature docs. Document stable purpose, entry points, invariants and
gotchas, rather than workflow status.

Hook wiring lives in `.claude/settings.json`. Hooks do not implement OpenSpec
lifecycle transitions and must not be bypassed. Review policy: [REVIEW.md](REVIEW.md).

## Skill loading and updates

Lifecycle/conditional/explicit utility policy is defined in FACTORY.md.
`.claude/settings.json` keeps gauntlet-loop, grilling, handoff, setup-update and
rescan-docs user-invocable-only. These remain available explicitly; exploration
may call grilling when the user requests interrogation. Conditional techniques
use narrow descriptions rather than global instructions to load them.

Superpowers is optional and remains installed if already present. Only selected
engineering techniques are relevant; its overlapping workflow responsibilities
are excluded by the factory policy. Measure actual technique usage before
considering removal. Use `/graft` for application navigation as described above. Factory workflow
boundaries take precedence over upstream skill suggestions to auto-refresh.

`make manifest` records hashes for template-owned instructions, factory docs,
scripts, and evals. `setup-update` uses that history to distinguish pristine
files from local customizations. OpenSpec-generated paths are excluded. New
helpers and shape-change ship with their callers; see [setup](.harness/docs/setup.md)
for migration and update commands.
